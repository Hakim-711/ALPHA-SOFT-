# تقرير QA شامل للمشروع

تاريخ الفحص: 2026-05-07  
نطاق الفحص: مشروع React + TypeScript كواجهة عربية RTL فوق ERPNext، مع مراجعة عامة لكل الموديولات، الصلاحيات، الربط، POS، التقارير، الأداء، الأمان، وتجربة المستخدم.

تحديث تنفيذي بعد التقرير: تم تنفيذ المرحلة الأولى من `Cash Shift / ورديات الكاشير` وإضافة صفحة `/cash-shifts` وربط POS بها بحيث لا يعتمد البيع بدون وردية مفتوحة. ما يزال مطلوبا اختبار حي على ERPNext الفعلي وإكمال الطباعة والمرتجعات وE2E.

## 1. الخلاصة التنفيذية

المشروع وصل إلى مرحلة جيدة كأساس منتج: يوجد هيكل موديولات واضح، ربط فعلي مع ERPNext، واجهة عربية، POS مستقل، صفحات مبيعات ومشتريات ومخزون وتحصيلات وصرف وتقارير وحسابات مستخدمين.

لكن المشروع لا يزال غير جاهز كمنتج تجاري نهائي لمحل أو سوبرماركت في مأرب أو اليمن بدون معالجة نواقص حرجة. أهم الفجوات ليست في الشكل فقط، بل في التشغيل اليومي: إغلاق الصندوق، المرتجعات، الطباعة، الاختبارات الآلية، الصلاحيات الدقيقة، الأداء مع البيانات الكبيرة، والعمل عند ضعف الإنترنت.

نتيجة الفحص العامة:

| الجانب | الحالة | الحكم |
| --- | --- | --- |
| TypeScript | ناجح | جيد |
| Lint | ناجح | جيد |
| Build | ناجح | جيد |
| Security audit | ناجح | لا توجد ثغرات npm متوسطة أو أعلى |
| Automated tests | غير موجود | نقص حرج |
| POS | قوي مبدئيا | يحتاج إغلاق صندوق ومرتجعات وطباعة وOffline أقوى |
| الصلاحيات | موجودة | تحتاج تشخيص وFallback أفضل |
| المشتريات | موجودة | تحتاج ربط أعمق بالاستلام والموردين والتقارير |
| التقارير | موجودة كمؤشرات تشغيلية | ليست تقارير محاسبية كاملة |
| الإعدادات | محلية فقط | ليست مصدرها ERPNext |
| التوثيق | موجود جزئيا | README ودليل التشغيل ناقصان |

- نظام الصلاحيات.
- البحث العام.

- العملاء، الموردين، الأصناف.
- المبيعات: Sales Order و Sales Invoice.
- المشتريات: Purchase Order و Purchase Invoice.
- التحصيلات والصرف.

- التقارير.

## 3. أوامر الفحص الآلي

تم تشغيل الفحوصات التالية:

```bash
npm run typecheck
npm run lint
npm audit --audit-level=moderate
npm run build
```

النتيجة:

- `typecheck`: ناجح.
- `lint`: ناجح.
- `audit`: لا توجد ثغرات بمستوى moderate أو أعلى.
- `build`: ناجح.

ملاحظة مهمة: لا يوجد سكربت `test` في `package.json` ولا توجد اختبارات فعلية Unit / Integration / E2E. هذا يعني أن نجاح البناء لا يكفي لضمان أن النظام آمن من الانكسار بعد التعديلات.

## 5. نتائج QA حسب الأولوية

## P0 - نواقص حرجة قبل الإنتاج

### 5.1 لا يوجد نظام اختبارات آلية

المشكلة: المشروع لا يحتوي على Vitest أو React Testing Library أو Playwright، ولا يوجد `npm test`.

الأثر:

- أي تعديل على POS أو الصلاحيات قد يكسر مسارا أساسيا بدون اكتشاف.
- لا يمكن ضمان أن البيع النقدي، الدين، الدفع الجزئي، الخروج، الصلاحيات، أو التقارير تعمل بعد كل تحديث.

المطلوب:

- إضافة Vitest لاختبار الحسابات والمنطق.
- إضافة React Testing Library للنماذج والمكونات.
- إضافة Playwright لاختبار سيناريوهات الكاشير والمتصفح.
- إضافة CI يشغل `typecheck + lint + tests + build`.

### 5.2 لا يوجد Cash Shift حقيقي

الموجود حاليا: صفحة `Daily Cash` تعرض تقرير صندوق من بيانات ERPNext.

النقص: لا يوجد نظام وردية/صندوق رسمي:

- فتح وردية.
- رصيد افتتاحي.
- تحديد الكاشير والفرع والصندوق.
- تسجيل المبيعات والتحصيلات داخل الوردية.
- جرد نقدي فعلي.
- إغلاق اليوم.
- منع البيع أو التعديل بعد الإغلاق إلا بصلاحية.
- فرق صندوق.
- توقيع/ملاحظة المدير.

الأثر: في محل حقيقي، هذه نقطة خطيرة لأن الكاشير يحتاج نهاية يوم واضحة، والمالك يحتاج يعرف الفرق بين المتوقع والفعلي.

المطلوب:

- إنشاء موديول `Cash Shift`.
- ربط POS بالوردية المفتوحة.
- منع اعتماد البيع إذا لا توجد وردية مفتوحة للكاشير.
- إنشاء تقرير إغلاق اليوم.

### 5.3 POS لا يدعم المرتجعات والاسترداد بشكل كامل

النقص:

- Return Invoice.
- Partial Refund.
- إرجاع صنف واحد من فاتورة.
- إرجاع نقدي أو إلى رصيد العميل.
- سبب المرتجع.
- صلاحية خاصة للمرتجع.
- طباعة إيصال مرتجع.

الأثر: أي سوبرماركت أو محل يحتاج المرتجعات يوميا. بدونها سيضطر المستخدم للرجوع إلى ERPNext أو عمل قيود يدوية.

المطلوب:

- شاشة مرتجع POS مستقلة.
- بحث برقم الفاتورة أو الباركود.
- تحديد الأصناف الراجعة.
- إنشاء Return Sales Invoice عبر ERPNext.
- ربط الاسترداد بالصندوق أو ذمة العميل.

### 5.4 Offline POS الحالي غير كاف للإنتاج

الموجود: طابور Offline محفوظ في `localStorage`.

النقص:

- `localStorage` ليس مناسبا لعمليات مالية طويلة أو كثيرة.
- لا توجد Idempotency Key مضمونة تمنع تكرار الفاتورة عند إعادة الإرسال.
- لا يوجد Conflict Resolution واضح.
- لا توجد شاشة مراجعة للطابور قبل المزامنة.
- لا توجد حماية من امتلاء التخزين أو حذف بيانات المتصفح.

الأثر: عند ضعف الإنترنت في اليمن، قد تتكرر فواتير أو تضيع عمليات إذا اعتمدنا على هذا المستوى فقط.

المطلوب:

- نقل الطابور إلى IndexedDB.
- إضافة `client_reference_id` لكل فاتورة POS.
- منع التكرار عند المزامنة.
- شاشة Offline Queue للكاشير/المدير.
- سجل مزامنة كامل.

### 5.5 لا توجد تأكيدات كافية قبل العمليات الخطرة

الموجود: POS لديه تأكيد عند إلغاء البيع الحالي.

النقص: صفحات المستندات مثل Sales Invoice / Sales Order / Purchase Invoice / Purchase Order / Collection / Disbursement / Stock قد تنفذ Submit أو Cancel مباشرة من الزر بدون حوار تأكيد موحد.

الأثر:

- خطر اعتماد أو إلغاء مستند بالخطأ.
- في ERP، الاعتماد والإلغاء ليسا مثل تعديل حقل عادي.

المطلوب:

- مكون موحد `ConfirmActionDialog`.
- سبب الإلغاء عند Cancel.
- إبراز أثر العملية: "سيؤثر على المخزون/الحسابات".

## P1 - نواقص عالية الأهمية

### 5.6 الصلاحيات تعمل، لكنها تحتاج تشخيص أفضل

الموجود:

- قراءة صلاحيات DocType.
- إخفاء عناصر من القائمة حسب الصلاحية.
- Admin/System Manager لهما bypass داخل hook.

المشكلة:

- إذا فشل جلب metadata للـ DocType، النظام يرجع صلاحيات كلها `false`.
- هذا قد يجعل البحث أو القائمة تظهر "لا توجد صلاحيات" حتى للمستخدم الذي يملك صلاحية، خصوصا عند مشاكل session أو metadata permission.
- لا توجد صفحة تشخيص تبين: المستخدم الحالي، أدواره، سبب إخفاء كل موديول.

المطلوب:

- إضافة Permission Diagnostics للمدير.
- عرض سبب تعطيل كل موديول.
- حفظ آخر صلاحيات ناجحة مؤقتا.
- فصل "لا توجد صلاحية" عن "فشل تحميل الصلاحيات".

### 5.7 البحث العام قد يكون ثقيلا

الموجود: البحث العام يبحث في عدة موديولات دفعة واحدة حسب الصلاحيات.

النقص:

- لا يوجد debounce واضح داخل hook.
- البحث ينفذ عدة طلبات متوازية.
- مع بيانات كبيرة، سيؤثر على الأداء.

المطلوب:

- Debounce 300-500ms.
- إلغاء الطلب السابق عند تغيير البحث.
- حد أقصى للموديولات في أول نتيجة.
- زر "بحث متقدم" بدلا من جلب كل شيء دائما.

### 5.8 التقارير تشغيلية وليست محاسبية كاملة

الموجود:

- تقارير مبيعات.
- ديون عملاء وموردين.
- مخزون ناقص.
- مشتريات مفتوحة.

النقص:

- لا توجد ميزانية عمومية.
- لا يوجد أرباح وخسائر رسمي.
- لا يوجد دفتر أستاذ كامل.
- لا يوجد ميزان مراجعة.
- لا يوجد تقرير فروقات عملة.
- لا يوجد تقرير أعمار ديون كامل.

المطلوب:

- إما استهلاك تقارير ERPNext الرسمية.
- أو بناء واجهات تعرض تقارير ERPNext المحاسبية بدون إعادة اختراع الحسابات.

### 5.9 الصندوق اليومي ليس إغلاق يوم

الموجود: `Daily Cash` يحسب من GL Entry وPayment Entry وPOS Sales.

المشكلة:

- يقرأ بيانات كثيرة وقد يصبح ثقيلا.
- لا يحفظ حالة إغلاق.
- لا يسجل النقد الفعلي.
- لا يمنع التعديل بعد الإغلاق.

المطلوب:

- تحويله إلى شاشة تشغيلية مرتبطة بـ Cash Shift.
- الإبقاء على التقرير كعرض، وليس كبديل للإغلاق.

### 5.10 إعدادات المحل محلية فقط

الموجود: `store-preferences.ts` يحفظ في `localStorage`.

المشكلة:

- الإعدادات تختلف من جهاز لجهاز.
- لا يراها المدير مركزيا.
- لا يتم ربطها بشركة/فرع/مستخدم.
- يمكن ضياعها عند تنظيف المتصفح.

المطلوب:

- حفظ الإعدادات المهمة في ERPNext كـ DocType/Single DocType مخصص أو داخل إعدادات الشركة/الفرع.
- استخدام `localStorage` فقط لتفضيلات شكلية مثل فتح/إغلاق لوحة جانبية.

### 5.11 الطباعة غير كافية

الموجود: استخدام `window.print` في بعض الأماكن.

النقص:

- لا يوجد قالب إيصال 80mm مخصص.
- لا يوجد إعداد طابعة.
- لا يوجد Cash Drawer integration.
- لا توجد طباعة مرتجع/إغلاق يوم/كشف حساب بشكل احترافي.

المطلوب:

- صفحة Print Layout مستقلة.
- CSS خاص للطباعة.
- دعم إيصال حراري.
- دعم ESC/POS لاحقا إن احتاج العميل.

## 6. QA للـ POS بالتفصيل

الـ POS يحتوي على:

- صفحة مستقلة عن الشريط الجانبي.
- بحث صنف/باركود.
- إضافة أصناف للسلة.
- كمية وسعر وخصم.
- بيع نقدي.
- بيع آجل.
- دفعة جزئية.
- حساب المتبقي والباقي.
- اختيار العميل.
- اختيار الشركة والمخزن وقائمة الأسعار.
- خيار التأثير على المخزون أو البيع بدون مخزون.
- سلات معلقة.
- إعدادات POS في Drawers.
- Offline Queue مبدئي.
- اختصارات مبدئية.
- تحذير مخزون.
- رسائل نجاح/خطأ.

## 6.2 سيناريوهات يجب أن تنجح قبل الإنتاج

| السيناريو | الحالة الحالية | المطلوب |
| --- | --- | --- |

## 6.3 مشاكل UX يجب مراقبتها

- تداخل الرسائل أو ظهور نص خلف شريط البحث عند اعتماد البيع.
- ارتفاع بعض البطاقات داخل السلة مما يخفي تفاصيل العميل والدين.
- الهيدر العلوي والسفلي يجب أن يبقيا ظاهرين دائما في شاشة الكاشير.
- التفاصيل الثانوية يجب أن تبقى داخل أزرار/Drawers حتى لا تصبح شاشة الكاشير مزدحمة.
- يجب أن يكون زر اعتماد البيع واضحا وثابتا.
- يجب أن تكون ألوان حالات البيع مختلفة وواضحة:
  - نقدي: أخضر/أزرق.
  - آجل: برتقالي/تحذيري.
  - جزئي: بنفسجي/أزرق.
  - خطأ مخزون: أحمر.

## 7. QA للصلاحيات والحسابات

## 7.1 الموجود

- موديول Accounts يدير ERPNext User.
- إنشاء وتعديل مستخدم.
- تفعيل/تعطيل المستخدم.
- إسناد أدوار ERPNext.
- إخفاء عناصر القائمة حسب صلاحيات DocType.

## 7.2 النواقص

- لا توجد مصفوفة صلاحيات سهلة للمدير.
- لا توجد قوالب أدوار جاهزة مثل:
  - مالك.
  - مدير.
  - كاشير.
  - محاسب.
  - أمين مخزن.
  - مندوب.
- لا يوجد شرح لماذا زر أو موديول مخفي.
- لا توجد شاشة "اختبار مستخدم" لرؤية النظام كما يراه المستخدم.
- كلمة المرور تعرض كحقل عادي من نوع password بدون زر إظهار/إخفاء.
- لا يوجد فرض سياسة كلمة مرور من الواجهة، مع أن ERPNext قد يفرضها خلفيا.

## 7.3 المطلوب

- Role Templates.
- Permission Matrix UI.
- Permission Diagnostics.
- زر إظهار/إخفاء كلمة المرور.
- تحذير عند إعطاء أدوار حساسة.
- منع المستخدم غير المدير من تعديل أدواره أو أدوار Administrator.

## 12. QA للأمان

## 12.1 نقاط جيدة

- لا يوجد اعتماد افتراضي على API key داخل المتصفح.
- Browser token auth تمت إزالته من الواجهة، والاعتماد الآن على Session/Cookies أو proxy آمن.
- الاعتماد الأساسي على Session/Cookies مناسب أكثر للواجهة.
- معالجة أخطاء API مركزية.

## 12.2 مخاطر

- يجب الاستمرار في منع أي إعادة إدخال لمفاتيح API داخل متغيرات `VITE_*`.
- لا توجد شاشة إدارة جلسات.
- لا يوجد Activity Log داخل الواجهة.
- لا توجد حماية UX من انتهاء الجلسة.
- لا توجد قيود واضحة على تعديل أدوار حساسة من الواجهة.

## 12.3 المطلوب

- استخدام Same-origin proxy/session في الإنتاج.
- منع نشر API secret داخل Vite client.
- Session expired modal.
- Activity history.
- حماية حساب Administrator.

## 13. QA للأداء

## 13.1 الجيد

- أغلب القوائم تستخدم pagination.
- React Query مستخدم للـ server state.
- build ناجح وحجم الحزم مقبول كبداية.

## 13.2 المخاطر

- Global Search قد يرسل عدة طلبات لكل كتابة.
- Daily Cash يجلب حتى 10,000 صف لكل Doctype في بعض الحالات.
- Reports تجلب 500 سجل وتجمع في العميل.
- لا توجد virtualized tables.
- لا يوجد caching strategy مفصل للتقارير الثقيلة.

## 13.3 المطلوب

- Debounce للبحث.
- Server reports بدل تجميع كبير في المتصفح.
- Virtual tables للبيانات الثقيلة.
- Lazy loading للموديولات الثقيلة.

## 14. QA للتجربة العربية RTL

## 14.1 الجيد

- الواجهة عربية وموجهة RTL.
- POS مناسب بصريا للكاشير بعد التحسينات.
- يوجد تركيز واضح على سوق اليمن ومأرب.

## 14.2 النواقص

- يجب تثبيت ترميز UTF-8 في جميع الأدوات والملفات وCI.
- يجب اختبار RTL على:
  - 1366x768.
  - 1920x1080.
  - Tablet.
  - Mobile.
- يجب اختبار تداخل النصوص داخل الأزرار والبطاقات.

## 17. الحكم النهائي

المشروع حاليا ليس ضعيفا كأساس تقني، لكنه غير مكتمل كمنتج تجاري نهائي. أفضل وصف دقيق:

> واجهة ERPNext عربية حديثة في مرحلة متقدمة من MVP، لكنها تحتاج طبقة تشغيل يومية واختبارات وصلاحيات وPOS Production Hardening قبل استخدامها في محل حقيقي بدون إشراف.

الهدف القادم يجب ألا يكون إضافة صفحات عشوائية. الهدف القادم يجب أن يكون إغلاق الفجوات الحرجة:

- Cash Shift.
- POS Returns.
- Automated QA.
- Permission Diagnostics.
- Print/Receipt.
- Offline reliability.

بعد هذه المرحلة سيبدأ المشروع يتحول من "واجهة جميلة فوق ERPNext" إلى "منتج ERP/POS حقيقي مناسب للسوق اليمني".
